# pica-server 重构设计文档

> 目标：在不推翻现有可运行系统的前提下，把「下载任务状态」从易失的内存里拿出来，
> 让 pica-server 具备**重启不丢任务、可断点续传、可观测、可自动恢复**的能力，
> 并把已跟 NAS 上青龙流水线（SQLite + CBZ + 115 + LANraragi）耦合的边界显式化。

本文只做设计，不改代码。

---

## 1. 现状梳理（基于实际代码）

### 1.1 工程结构

仓库 `picacomic-downloader-main` 是一个混合仓库：

| 目录 | 内容 |
| --- | --- |
| `src-server/` | Rust Web 后端（axum）——**本次重构对象** |
| `src-tauri/` | Tauri 桌面壳（历史遗留） |
| `src/` | 前端（Vue + Vite，构建产物进 `dist/`） |
| `Dockerfile` / `docker-compose.yml` | NAS 部署（容器名 `pica-server`，端口 8080） |

`src-server/src` 共约 **3300 行**，模块划分：

```

logger.rs          224   tracing 分层 + 文件滚动 + 日志事件
```

### 1.2 下载链路（当前实现）

```
routes.rs  POST /api/download
   └─> commands::create_download_task
        └─> DownloadManager::create_download_task(comic, chapter_id)
             ├─ 检查 HashMap 里是否已有同 chapter_id 的活跃任务
             ├─ DownloadTask::new(...)
             ├─ tokio::spawn(task.process())        <-- 状态只活在堆内存里
             └─ download_tasks.insert(chapter_id, task)
```

`DownloadManager` 的字段（`download_manager.rs:34-40`）：

```rust
pub struct DownloadManager {
    app: AppContext,
    chapter_sem: Arc<Semaphore>,      // 章节级并发
    img_sem: Arc<Semaphore>,          // 图片级并发
    byte_per_sec: Arc<AtomicU64>,     // 下载速率统计
    download_tasks: Arc<RwLock<HashMap<String, DownloadTask>>>,  // ← 唯一状态源
}
```

`DownloadTask` 的进度靠两个 `AtomicU32`（`downloaded_img_count` / `total_img_count`）
和一条 `tokio::sync::watch` 通道承载状态机：

```rust
enum DownloadTaskState { Pending, Downloading, Paused, Cancelled, Completed, Failed }
```

`DownloadImgTask::process()` 用 `tokio::select!` 同时监听「图片下载完成」和
「状态变化」，实现暂停/取消时能及时让出 `img_sem` 许可（`download_manager.rs:750-776`）。
这套暂停/取消逻辑本身设计得不错，问题在**持久化与恢复**。

### 1.3 已确认的缺陷

| 编号 | 缺陷 | 位置 | 影响 |
| --- | --- | --- | --- |
| **D1** | 任务状态纯内存，进程重启即全部丢失 | `download_manager.rs:39` | 容器一重启（NAS 重启、`docker compose up -d --build`），所有 `Pending`/`Downloading` 任务凭空消失，前端面板清空，用户不知道哪些下了哪些没下 |
| **D2** | `shutdown()` 只把任务标记为 `Cancelled`，不做落盘 | `download_manager.rs:74-79` | 改并发度配置会触发 `reload_download_manager()`（`context.rs:125-133`），**静默取消所有正在下载的任务**，且不通知用户 |
| **D3** | 章节完整性判定过粗 | `download_manager.rs:286-299` | `downloaded_img_count != total_img_count` 直接判 `Failed`，**单张图超时导致整个章节重头再来**。实际观察到的主因就是图片 CDN 超时 |
| **D4** | 失败无重试、无退避 | `DownloadImgTask::download_img` 出错仅 `return` | 一次超时 = 一张图永久缺失 |
| **D5** | `chapter_id` 与后处理流水线脱节 | `submit_state.json` / SQLite 在青龙侧 | 下载状态与 `is_downloaded` 字段两套真相源，对不上时需要人工 `submit_state.json` 重置 |
| **D6** | 日志曾经 TRACE 级刷盘 | `logger.rs`（**已修复**，改为 INFO 默认 + `PICA_LOG_LEVEL` 覆盖） | 20G 日志爆炸，已通过工作区未提交改动解决 |
| **D7** | 无任务列表分页/清理 | `task_snapshot()` 返回全部 | 长期运行后 `HashMap` 无限增长，`Completed` 任务永不回收 |
| **D8** | `DownloadManager` 重建导致信号量许可泄漏 | `context.rs:130` | 旧 manager 的 `shutdown()` 只发状态，已 spawn 的 task 仍持有旧 `img_sem`，新旧两套信号量并存，实际并发是配置值的两倍 |

### 1.4 修复状态确认

- **D6 已修复**：`logger.rs` 默认级别已是 `INFO`，可用 `PICA_LOG_LEVEL` 覆盖为 `trace/debug/warn/error`。
  该改动目前是工作区的未提交修改（`M src-server/src/logger.rs`），需提交并部署。
- 其他缺陷均未处理。

## 2. 重构目标与非目标

### 2.1 目标

1. **任务持久化**：进程重启后，未完成任务能自动恢复（D1、D2）。
2. **断点续传**：章节级 + 图片级双重续传，已下载的图片不重复下载（D3、D4）。
3. **状态单一真相源**：pica-server 自己的 SQLite 记录下载状态，青龙侧只读（D5）。
4. **可观测**：任务进度、失败原因、重试次数可通过 API 与 WebSocket 查询。
5. **可运维**：任务可查询、可清理、可手动重试；并发配置变更不丢任务（D7、D8）。

### 2.2 非目标（本次不做）

- 不改前端框架、不改 UI 结构（仅新增接口 + 可选的状态展示）。
- 不改哔咔 API 签名逻辑（`pica_client.rs:27-29` 的硬编码密钥保持原样）。
- 不替换青龙（Qinglong）流水线，只调整边界契约。
- 不引入消息队列 / Redis 等外部依赖 —— NAS 上多一个组件就多一个故障点。

## 3. 目标架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────┐
│  api/routes.rs  (HTTP)   api/ws.rs (WebSocket)       │
└───────────────────────┬──────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────┐
│  scheduler/  —— 调度层（新增）                        │
│   · TaskQueue      待执行队列，按优先级出队           │
│   · ConcurrencyController  章节/图片信号量（可热更新） │
│   · Recovery       启动时扫描 DB，重建未完成任务       │
└───────────────────────┬──────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────┐
│  store/  —— 持久化层（新增，SQLite）                  │
│   · TaskRepo     download_task 表                    │
│   · ImageRepo    download_image 表（断点续传核心）    │
│   · Migrations   版本化建表                          │
└───────────────────────┬──────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────┐
│  download/  —— 执行层（由 download_manager 拆分）     │
│   · ChapterDownloader   章节流程编排                 │
│   · ImageDownloader     单图下载 + 重试              │
│   · ImageConverter      rayon 图像转换（保持不变）    │
└───────────────────────┬──────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────┐
│  pica_client.rs  ·  config.rs  ·  event_bus.rs       │
│  （保持不变，仅微调）                                 │
└──────────────────────────────────────────────────────┘
```

### 3.2 关键决策

#### 决策 1：持久化用 SQLite，不引外部组件

- 复用 NAS 上已有的 SQLite 生态（青龙侧已经在用 `bica_comics.db`）。
- 新增独立库 `pica_server.db`，放在 `PICA_DATA_DIR` 下，**不与青龙的库混用**。
- 用 `rusqlite` + `r2d2` 连接池，或 `sqlx`（编译期检查）。
  **推荐 `rusqlite` + `bundled` feature**：交叉编译到 Docker 镜像时不需要系统 libsqlite3，
  且避免 `sqlx` 的异步宏给 3300 行的小项目带来编译负担。

#### 决策 2：双层任务模型（章节 + 图片）

```sql
-- 章节级任务
CREATE TABLE download_task (
    chapter_id      TEXT PRIMARY KEY,
    comic_id        TEXT NOT NULL,
    comic_title     TEXT NOT NULL,
    chapter_title   TEXT NOT NULL,
    chapter_order   INTEGER NOT NULL,
    dir_fmt         TEXT NOT NULL,   -- 落盘时的目录格式快照，防止配置变更后找不到文件
    state           TEXT NOT NULL,   -- pending/downloading/paused/cancelled/completed/failed
    total_img_count INTEGER NOT NULL DEFAULT 0,
    done_img_count  INTEGER NOT NULL DEFAULT 0,
    retry_count     INTEGER NOT NULL DEFAULT 0,
    last_error      TEXT,
    created_at      INTEGER NOT NULL,
    updated_at      INTEGER NOT NULL
);
CREATE INDEX idx_task_state ON download_task(state);

-- 图片级任务：断点续传的核心
CREATE TABLE download_image (
    chapter_id  TEXT NOT NULL,
    img_index   INTEGER NOT NULL,
    url         TEXT NOT NULL,
    state       TEXT NOT NULL,   -- pending/done/failed
    retry_count INTEGER NOT NULL DEFAULT 0,
    last_error  TEXT,
    bytes       INTEGER,
    updated_at  INTEGER NOT NULL,
    PRIMARY KEY (chapter_id, img_index),
    FOREIGN KEY (chapter_id) REFERENCES download_task(chapter_id) ON DELETE CASCADE
);
```

**为什么图片级要单独建表**：当前 D3 的根因是「一张图失败 = 整章重来」。
有了 `download_image.state`，恢复时只需重下 `state != 'done'` 的图片，
章节级完整性判定也从「计数相等」变成「查 `count(*) where state != 'done'` 为 0」，
既精确又天然幂等。

#### 决策 3：状态机显式化 + 单向迁移

```
                    ┌─────────────┐
                    │   pending   │◄──────── resume ────────┐
                    └──────┬──────┘                         │
                           │ schedule                     │
                           ▼                              │
                    ┌─────────────┐                         │
             ┌─────►│ downloading │──── pause ────► paused ─┘
             │      └──────┬──────┘
             │             │
        retry│             ├── all images done ──► completed
             │             │
             │             └── unrecoverable ───► failed
             │                          │
             └──────── manual retry ────┘
```

约束：
- `completed` 是终态，除非人工 `DELETE` 后重建。
- `failed` 可在人工触发或自动重试策略下回到 `pending`。
- `cancelled` 不自动恢复，需人工干预。
- 每次状态迁移写 DB + 发事件，两者在同一事务边界内（先写 DB 再发事件）。

#### 决策 4：并发控制器可热更新，不再重建 Manager

D8 的根因是 `reload_download_manager()` 整个重建。改为：

```rust
pub struct ConcurrencyController {
    chapter_sem: Arc<Semaphore>,   // 用 Semaphore::add_permits / forget_permits 动态调整
    img_sem: Arc<Semaphore>,
}
```

`tokio::sync::Semaphore` 支持 `add_permits(n)` 增加、`forget_permits(n)` 收缩。
配置变更时**原地调整许可数**，任务对象不重建，`HashMap` 不清空。

需要注意 `forget_permits` 收缩时若许可已被持有，会等待归还后才真正生效 —— 这符合预期。

#### 决策 5：恢复流程（启动时）

```
main()
 └─> Store::open(data_dir/pica_server.db)
      └─> run_migrations()
      └─> Recovery::scan()
           ├─ 把 state='downloading' 的任务改回 'pending'    （进程崩了，不可能还在下）
           ├─ 对每个 'pending' 任务：
           │    ├─ 如果 download_image 全 done → 直接置 completed
           │    └─ 否则重新入队 TaskQueue
           └─ 对每个 'paused' 任务：保持 paused，等人工恢复
```

**关键点**：`downloading` 是**进程内瞬态**，重启后一律回退到 `pending`。
不要试图保留它 —— 那会让恢复逻辑复杂化且没有收益。

## 4. 迁移路径（分四步，每步可独立发布）

### Step 1：提交日志修复 + 止血（低风险，立即做）

- 提交工作区的 `logger.rs` 改动：
  ```bash
  git add src-server/src/logger.rs
  git commit -m "fix(log): 日志级别 TRACE→INFO，修复 20G 日志爆炸"
  git push
  ```
- 在 NAS 上重建镜像并部署 `1a3c111`（HTML 检测 + BMP 支持）与 `8215e10`（bmp feature 精简）。
- 运维侧：截断/归档 20G 日志。
- **不改代码逻辑**，先把地雷排掉。

### Step 2：引入 Store 层，双写（中风险）

- 新增 `store/` 模块与 `pica_server.db`。
- `DownloadManager` 的每次状态迁移**同时**写内存 `HashMap` 和 DB。
- 图片下载成功后写 `download_image.state='done'`。
- 此时恢复逻辑**尚未启用**，DB 只作为旁路记录。
- 验证点：跑一轮完整下载，确认 DB 里的 `done_img_count` 与前端显示的进度一致。

### Step 3：切换真相源到 DB，启用恢复（高风险，需要停机窗口）

- 删除 `download_tasks: HashMap`，`DownloadManager` 改为无状态的调度器。
- `task_snapshot()` 改为查 DB。
- 实现 `Recovery::scan()`，在 `init_runtime()` 之后调用。
- 修复 D8：`reload_download_manager()` 改为 `ConcurrencyController::update()`。
- 验证点：
  1. 启动下载 → 中途 `docker compose restart` → 确认任务自动继续且已下载图片未重复下载。
  2. 改 `imgConcurrency` → 确认任务不中断。
  3. 制造单图超时 → 确认只重试该图，章节不整体失败。

### Step 4：与青龙流水线对齐（中风险）

- 明确契约：pica-server 负责「下载 + 落盘到 `/comic-download`」，
  青龙负责「打包 CBZ + 上传 115 + 写 `is_downloaded`」。
- pica-server 新增只读视图 `GET /api/tasks?state=completed&since=<ts>`，
  供青龙的 `pika提交` 任务拉取，逐步**取代** `submit_state.json`。
- 过渡期两套并存：青龙仍读 `submit_state.json`，但同时可校验 API 结果，比对差异。

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| SQLite 写并发（章节并发 3 + 图片并发 20） | 单写连接 + WAL 模式；写操作集中在状态迁移点，不在图片下载热路径上（图片成功只更新一行，可批量合并） |
| DB 文件损坏 | 启动时 `PRAGMA integrity_check`；损坏则重命名旧库并重建，同时把内存状态降级为「无历史」，不阻塞服务启动 |
| 迁移期间新旧状态不一致 | Step 2 的双写阶段专门用于比对；不一致时以 DB 为准 |
| 恢复时磁盘上已有半成品目录 | 现有 `.下载中-{name}` 临时目录约定（`download_manager.rs:1128`）已经能区分完整与未完整，保留该约定 |
| 配置变更导致目录格式变化 | `download_task.dir_fmt` 存快照，恢复时用任务自身快照而非当前配置，避免找不到已下载文件 |
| 恢复大量任务导致启动雪崩 | `Recovery::scan()` 只标记状态、入队，不立即下载；由 `TaskQueue` 按并发上限逐步放行 |

## 7. 验收标准

1. **重启不丢**：下载 10 个章节，中途重启容器，重启后 10 个任务全部出现在列表中，
   状态为 `pending` 或继续 `downloading`，已下载图片数量保留。
2. **不重复下载**：上述场景中，磁盘上已存在的图片不被重新请求（可通过日志计数验证）。
3. **单图失败不炸章节**：人为让某张图 URL 返回 500，该图重试 N 次后标记 `failed`，
   章节状态为 `failed` 且 `last_error` 指向该图；其余图片已全部落盘。
   手动重试后只需下载那 1 张。
4. **配置热更新**：下载过程中把 `imgConcurrency` 从 20 改成 10，任务继续，不中断。
5. **日志可控**：默认 INFO 下，一次完整章节下载产生的日志不超过 200 行；
   设 `PICA_LOG_LEVEL=trace` 可恢复详细日志。
6. **API 契约**：青龙的 `pika提交` 任务能在不改动逻辑的情况下从 `GET /api/tasks` 拿到
   与 `submit_state.json` 等价的已完成章节列表。

## 9. 附：当前代码中的「不要动」清单

重构时容易顺手改坏的地方：

1. `main.rs:82-88` 的 SPA fallback —— 注释记录了 `not_found_service` 与
   双 `fallback_service` 两个坑，保持 `.fallback(ServeFile)`。
2. `pica_client.rs:87` 的 URL 拼接 —— `format!("{}/{}", base_url.trim_end_matches('/'), path.trim_start_matches('/'))`
   是修复「配置缺尾斜杠导致畸形 URL + 422 伪装成签名错误」的关键。
